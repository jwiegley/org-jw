1. Stale chunk deletion runs one `DELETE FROM entry_embeddings WHERE entry_id = ?` per candidate (embedEntries, ~line 78). Replace with a single `DELETE ... WHERE entry_id = ANY(?)` per batch or one set-based statement over all candidates.

* DONE [#A] Sync change detection hashes Loc (file path + byte offsets), causing full-corpus rewrite
:PROPERTIES:
:OBR_SCHEMA_VERSION: 17
:ID:       org-jw-fix-entry-hash-loc-free-xqn
:LABELS:   []
:ISSUE_TYPE: bug
:CREATED:  [2026-09-11 Fri 09:50]
:MODIFIED: [2026-09-11 Fri 10:43]
:CREATED_BY: johnw
:FINISHED: [2026-09-11 Fri 10:43]
:CLOSE_REASON: computeEntryHash now serializes body/stamps/log entries through content-only projections (blockInfo/stampInfo/insertLogEntry mirrors) instead of derived Show, which embedded Loc (file path + byte offset). Hash carries v2: version marker; computeEntryHash exported; regression suite EntryHashTest (5 cases) proves Loc-independence + content-sensitivity. Verified: cabal build all -Werror clean, 14/14 org-db tests, fourmolu/hlint clean, make lint identical to baseline (16 pre-existing missing-asset errors; 0 round-trip failures).
:SOURCE_REPO: org-jw
:SOURCE_REPO_PATH: /Users/johnw/src/sys/org-jw
:ORIGINAL_SIZE: 0
:END:

`computeEntryHash` (org-db/src/Org/DB/Store.hs:273) serializes `entry ^. entryBody`, `entry ^. entryStamps`, and `entry ^. entryLogEntries` via `show`. All three types carry `Loc { _file :: FilePath, _pos :: Int }` (org-types/src/Org/Types.hs:54), which derives `Show`, so the "content hash" of every entry changes when:

1. Any byte earlier in the file changes — every later entry's `_pos` shifts, rewriting all following entries in the file.
2. The path form changes — `Loc._file` is the raw CLI path (org-parse/src/Org/Parse.hs:36), verbatim from `parseOrgFile cfg path`.

This is the root cause of the full-corpus rewrite observed on the `org` PostgreSQL database (62,443 per-entry child-table DELETEs ≈ 99.3% of all entries in one window, plus full re-embedding).

Fix: replace the three `show`-based components with loc-free serialization that mirrors exactly what the database stores:

- Body blocks: reuse `blockInfo` minus the byte offset — (block_type, content, drawer_type, drawer_name) joined with "\0". This also correctly stops hashing InlineTask nested bodies, which are not persisted by `insertBody`.
- Stamps: mirror `insertStampSQL` fields — (stamp_type, time_kind, day, day_end, time_start, time_end, suffix_kind, suffix_num, suffix_span, suffix_larger_num, suffix_larger_span).
- Log entries: mirror `insertLogEntry` — (log_type, time fields, from/to keywords, orig-time fields, duration, nested loc-free body); LogBook recurses.

Prefix the new hash with a version marker ("v2:") so the one-time invalidation of all stored hashes is explicit and future hash-semantics changes are detectable. Expected one-time cost after landing: every stored hash mismatches once → one full rewrite + re-embed pass; permanent stability thereafter.

Discovered while designing the loc-free entry hash (discovered-from org-jw-fix-entry-hash-loc-free-xqn).

`blockInfo` (org-db/src/Org/DB/Store.hs) maps `InlineTask loc _` to ("inline_task", Nothing, pos, Nothing, Nothing) — the nested Body is discarded. `insertBody` therefore persists an InlineTask as a single row with content NULL and never recurses into its nested blocks. Consequences:

- Inline-task content is invisible to entry_embeddings (combinedTextExpr reads entry_body_blocks WHERE content IS NOT NULL).
- The old `show`-based entry hash DID include nested content, so editing an inline task's text caused churn (entry marked changed) while the DB stored nothing different. The new loc-free hash drops it, matching the DB — but the content is still lost to search.

Fix: persist nested inline-task blocks (e.g. child rows or a flattened content column) and include them in embeddings; decide whether the entry hash should then cover them again. Check whether the corpus actually contains InlineTask blocks before investing.

Full verification: cabal build all clean, 14/14 org-db tests, fourmolu/hlint clean, make lint == 16-error baseline, 0 round-trip failures.
:SOURCE_REPO: org-jw
:SOURCE_REPO_PATH: /Users/johnw/src/sys/org-jw
:ORIGINAL_SIZE: 0
:END:

`upsertEntrySQL` (org-db/src/Org/DB/Store.hs:885-895) unconditionally nulls `embedding_hash` and `title_embedding` on conflict:

    ON CONFLICT (id) DO UPDATE SET ... embedding_hash = NULL, title_embedding = NULL

This forces a full re-embed whenever the upsert branch fires for an entry whose content is byte-identical — e.g. duplicate :ID: collisions across files, or a file-row miss (path form change, re-init) that re-inserts every entry in the file via `insertEntryFull`.

Fix: null the embeddings only when the entry's content hash actually changed:

    embedding_hash = CASE WHEN entries.hash IS NOT DISTINCT FROM EXCLUDED.hash
                           THEN entries.embedding_hash ELSE NULL END
    title_embedding = CASE WHEN entries.hash IS NOT DISTINCT FROM EXCLUDED.hash
                           THEN entries.title_embedding ELSE NULL END

Verification is meaningful only after the loc-free hash fix (org-jw-fix-entry-hash-loc-free-xqn): re-storing an unchanged file with stable IDs must leave embedding_hash and title_embedding intact.

Fix: carry an explicit version marker in entries.hash (e.g. "v2:" prefix on the loc-free serialization landed by the hash fix), document the convention in computeEntryHash, and confirm the one-time invalidation of pre-marker hashes behaves as expected. This may largely already be delivered by the hash fix; this issue exists to make the convention explicit and documented rather than incidental.
